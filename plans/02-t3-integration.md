# T3 Code integration architecture for a Rust streaming harness

Status: research and proposed design, 2026-11-15. This is a source-based plan, not an implementation or a claim of runtime compatibility. Upstream `main` resolved to commit [`86dbf2abd18e631da1061f3a2489da603b2cc242`](https://github.com/pingdotgg/t3code/commit/86dbf2abd18e631da1061f3a2489da603b2cc242), committed 2026-11-15 16:51:40 -08:00. All upstream paths below link to that immutable revision; recheck before implementation because this project changes quickly. The checkout was read, not built or run, and no live provider, credentials, performance, or wire interoperability was tested. References to Inspector are observations in the local [feature inventory](../inspector-feature-inventory/INSPECTOR-FEATURE-INVENTORY.md), not a license to reuse its proprietary implementation.

## Decision and boundaries

Build a **Rust-owned local harness and visual read model around an existing T3 server**. T3 remains authoritative for projects, workspaces, providers, thread/run lifecycle, permissions and its own durable state. Rust owns connection management, a versioned normalized event API, its own optional observation/history store, and the gallery/Inspector-style presentation. It must not write T3's SQLite, impersonate an injected provider session, parse provider logs as the authoritative state, or assume a filesystem event was caused by a particular agent.

Use two explicitly separate integration planes:

1. **Supported control/read plane: T3's outside-agent HTTP MCP endpoint.** Discover capabilities via `tools/list`, use OAuth for an external client, and use thread/project tools for launch, send, read, wait, and interrupt when actually exposed and authorized. For a same-host first milestone, wrap `t3 thread ... --json` as a simpler adapter. Neither supplies a proven push stream of all intermediate thread events.
2. **Streaming plane: opt-in T3 client RPC compatibility adapter.** An independently authenticated environment client subscribes to the same Effect RPC/WebSocket contracts as the T3 app. This provides the most direct route to live projection updates, but is a compatibility commitment, not a documented stable third-party streaming SDK. Start with a small pinned TypeScript bridge using upstream client runtime, speaking versioned NDJSON to Rust; only replace it with native Rust after capturing and passing real wire conformance tests. The MCP OAuth grant is deliberately restricted to `/mcp` and cannot authorize `/ws`.

On missing/incompatible stream support, explicitly degrade to MCP/CLI incremental reads and show **polling / partial detail**, not a fabricated token stream. Do not spin up another T3 server or take over its lifecycle by default. A user-selected, isolated T3 instance may be launched separately when required, with its own data directory.

```text
  T3 environment / workspace host
  ┌────────────────────────────────────────────────────────────┐
  │ providers ⇄ T3 provider adapters → orchestration + SQLite  │
  │       OAuth /mcp           authenticated /ws Effect RPC   │
  │             ↑                            ↑                 │
  │    Rust MCP control          pinned TS bridge (optional)   │
  │             └─────────────┬──────────────┘                 │
  │          Rust supervisor + reducer + optional event store  │
  │             ↑                             │                │
  │   Live Gallery watcher ── observed files ─┤                │
  │                                           ↓                │
  │         localhost Axum API / SSE → visual client           │
  └────────────────────────────────────────────────────────────┘
```

The server owns the real workspace, potentially on another machine. A Rust gallery watcher sees only its own machine's files. Never reinterpret a remote T3 path as a local path: disable local artifact viewing for remote environments until a separately authenticated remote file/asset adapter is implemented and verified.

## Verified upstream surfaces

### Starting and controlling T3

- The [README](https://github.com/pingdotgg/t3code/blob/86dbf2abd18e631da1061f3a2489da603b2cc242/README.md) describes `t3` as launching the server/web app. [`cli/server.ts`](https://github.com/pingdotgg/t3code/blob/86dbf2abd18e631da1061f3a2489da603b2cc242/apps/server/src/cli/server.ts) defines `t3 serve`, a foreground, no-browser server with pairing details; it does not bootstrap a project. [`cli/config.ts`](https://github.com/pingdotgg/t3code/blob/86dbf2abd18e631da1061f3a2489da603b2cc242/apps/server/src/cli/config.ts) defines `--host`, `--port`, `--no-browser`, `--base-dir` and associated `T3CODE_*` configuration. A running server using that base directory is detected. If a managed instance is added, choose a dedicated base directory, record PID/ownership, discover its actual endpoint, and only stop a process the harness started. Do not assume a default port or silently reuse the user's production database.
- [Outside agents](https://github.com/pingdotgg/t3code/blob/86dbf2abd18e631da1061f3a2489da603b2cc242/docs/user/outside-agents.md) documents `<environment-origin>/mcp`, OAuth, and host CLI use. Same-host examples are `t3 thread start . "..."`, `t3 thread send <id> "..." --wait`, `t3 thread show <id>`, and `t3 thread list`. `-` reads a message from stdin. The [actual CLI implementation](https://github.com/pingdotgg/t3code/blob/86dbf2abd18e631da1061f3a2489da603b2cc242/apps/server/src/cli/thread.ts) adds `--json`, start `--title`, paired `--provider`/`--model`, `--worktree <base-ref>`, and optional `--branch`; send queues instead of interrupting. `--wait --json` emits a terminal object with thread/run IDs, status, reply and error; exit 1 denotes failed/stopped, exit 2 a pending answer. It waits using MCP tools and reads final text, **not live stdout tokens**. A run and its background/delegated settlement are distinct; `waitForRun` optionally follows wakes. Preserve status and process exit independently.
- Use `tokio::process::Command` with argument arrays and stdin, never shell interpolation; cap stdout/stderr, propagate cancellation and timeouts, parse JSON only after process exit, and retain thread/run IDs even on nonzero exits. A killed CLI waiter is not evidence that its server-owned run stopped. For ambiguous launch failure, reconcile with T3 before retrying: the documented MCP launch has **no retry key**. `t3_thread_send` supports a `clientRequestId` for idempotency; reuse it only for a retry of the same intent. See [MCP orchestration](https://github.com/pingdotgg/t3code/blob/86dbf2abd18e631da1061f3a2489da603b2cc242/docs/orchestration-v2/orchestrator-mcp-server.md).
- For MCP use `t3_thread_list`, `t3_thread_read`, `t3_thread_launch`, `t3_thread_send`, `t3_thread_wait`, and the appropriate interrupt/request tools as discovered. `t3_thread_read` has cursor paging (`afterPosition`, `nextPosition`, `hasMore`; `beforePosition` for older items), bounded text and a separate `activity` view. Text truncation and pagination must be visible, not silently presented as full history. A wait timeout does not imply a stopped run. Use returned thread links verbatim where shown to users.

### Authentication and authority

T3's [environment authentication](https://github.com/pingdotgg/t3code/blob/86dbf2abd18e631da1061f3a2489da603b2cc242/docs/internals/environment-auth.md) says outside MCP OAuth clients use authorization code + PKCE, obtain an `mcp-client` session with read-only or a runtime-mode ceiling, and are refused by other HTTP/WebSocket paths. MCP OAuth requires localhost or HTTPS for sign-in, not arbitrary HTTP LAN. This is a hard architectural boundary, not a missing header to work around.

An environment client uses its own scoped session. Browser cookies may authenticate socket upgrades; bearer/DPoP clients obtain a short-lived WebSocket ticket over authenticated HTTP. DPoP uses a proof bound to the key; per-method RPC authorization still applies. See [`auth/http.ts`](https://github.com/pingdotgg/t3code/blob/86dbf2abd18e631da1061f3a2489da603b2cc242/apps/server/src/auth/http.ts), [`RpcAuthorization.ts`](https://github.com/pingdotgg/t3code/blob/86dbf2abd18e631da1061f3a2489da603b2cc242/apps/server/src/auth/RpcAuthorization.ts), and [connection runtime](https://github.com/pingdotgg/t3code/blob/86dbf2abd18e631da1061f3a2489da603b2cc242/docs/internals/connection-runtime.md). Acquire separate least-privilege credentials with the normal pairing flow; fail visibly if the necessary grant is unavailable. Keep secrets out of argv, browser URLs, logs, persisted events, diagnostics, and screenshots. Do not use the injected parent-thread bearer token for an external app. Remote networking requires an intentional deployment/auth design; default the Rust listener to loopback.

### Streaming and wire behavior

- The [RPC contract](https://github.com/pingdotgg/t3code/blob/86dbf2abd18e631da1061f3a2489da603b2cc242/packages/contracts/src/rpc.ts), [V2 domain schemas and method names](https://github.com/pingdotgg/t3code/blob/86dbf2abd18e631da1061f3a2489da603b2cc242/packages/contracts/src/orchestrationV2.ts), server [`ws.ts`](https://github.com/pingdotgg/t3code/blob/86dbf2abd18e631da1061f3a2489da603b2cc242/apps/server/src/ws.ts), and [client RPC session](https://github.com/pingdotgg/t3code/blob/86dbf2abd18e631da1061f3a2489da603b2cc242/packages/client-runtime/src/rpc/session.ts) establish authenticated `/ws`, Effect RPC JSON serialization, and method-specific typed streams. Effect RPC frames are not proven to be plain JSON-RPC or SSE. Protocol negotiation, frame splitting, multiplexing, cancellation, heartbeats and errors must be taken from the actual pinned client/server, not invented. Upstream tests use `/ws?orchestrationProtocol=2`; current client also opts into socket frame parts. Do not claim a sample raw request works until a captured end-to-end test proves it.
- Subscribe `orchestration.subscribeThread` with `{threadId, afterSequence?}`. Its items include `snapshot` (projection and `snapshotSequence`), `event` (sequence and domain event), and optionally `synchronized` when requested. Optional bounded/compact/deduplicated forms change decoding; initially omit opt-in compression fields and implement only after compatibility tests. `orchestration.subscribeShell` provides project/thread shells; `orchestration.getThreadFamily` retrieves root, forks and subagent family, including idle children that an optimized shell can omit. See [schemas](https://github.com/pingdotgg/t3code/blob/86dbf2abd18e631da1061f3a2489da603b2cc242/packages/contracts/src/orchestrationV2.ts).
- Text arrives as evolving projected message/turn-item updates; do not blindly append full snapshots or assume token-level deltas. Providers differ, and [assistant streaming](https://github.com/pingdotgg/t3code/blob/86dbf2abd18e631da1061f3a2489da603b2cc242/apps/server/src/orchestration-v2/assistantStreaming.ts) includes a paragraph mode and idle flush. Apply upstream semantics per item ID, replace when appropriate, and display the actual streaming state. Test Unicode splits, replacements, duplicates, and finalization. Reasoning/tool output may be absent or restricted.
- `orchestration.subscribeCommandOutput` takes `{threadId, itemId}` and returns **unpersisted, bounded** `{kind: "replace" | "append", text, truncated, running}` frames. `replace` resets the current tail, `append` extends it, `truncated` means bytes were lost, and `running: false` ends the stream. Cursor/style escapes need proper terminal rendering; safe plain text is acceptable initially. The stream is distinct from durable thread events, and reconnect cannot be advertised as complete output. See [contract](https://github.com/pingdotgg/t3code/blob/86dbf2abd18e631da1061f3a2489da603b2cc242/packages/contracts/src/orchestrationV2.ts) and [`CommandOutputHub.ts`](https://github.com/pingdotgg/t3code/blob/86dbf2abd18e631da1061f3a2489da603b2cc242/apps/server/src/orchestration-v2/CommandOutputHub.ts).
- Snapshots carry a global stored-event sequence. Apply events strictly newer than the snapshot and last applied cursor, but **do not require consecutive sequence numbers within a filtered thread**. Persist projection and cursor atomically. On reconnect request `afterSequence`; accept either replay or a replacement snapshot and reconcile rather than merging old rows into the new authoritative projection. Upstream [`ThreadStream.ts`](https://github.com/pingdotgg/t3code/blob/86dbf2abd18e631da1061f3a2489da603b2cc242/apps/server/src/orchestration-v2/ThreadStream.ts) limits replay to 128 events and 1 MiB encoded/raw thresholds; its actual eligibility and pruning checks may change. Handle unknown event/item types like the upstream forward-compatible decoder: retain/report unknowns and advance only when safe, then resnapshot if semantic state cannot be trusted. A known malformed event is an error, not an unknown event.

### Providers, delegation, and workspaces

T3 routes by **provider instance**, not just provider name. The [provider constraints](https://github.com/pingdotgg/t3code/blob/86dbf2abd18e631da1061f3a2489da603b2cc242/docs/internals/providers.md), [capability design](https://github.com/pingdotgg/t3code/blob/86dbf2abd18e631da1061f3a2489da603b2cc242/docs/orchestration-v2/provider-capability-system.md), and [adapters](https://github.com/pingdotgg/t3code/tree/86dbf2abd18e631da1061f3a2489da603b2cc242/apps/server/src/orchestration-v2/Adapters) describe different process/account lifecycles and per-provider streaming, native fork, rollback, permissions, and steering. Query actual instance/model availability and options, do not hardcode provider or token-stream parity. Codex async questions can remain pending after a turn ends; preserve the server's request identity and response capability. Model switch/resume is a T3 operation, not a Rust-side conversation copy.

A T3 `delegate_task` creates an app-owned child thread under an **active parent provider-session credential**; an external MCP client has no calling thread and is refused. Outside callers can launch ordinary top-level threads, not turn them into T3 delegated children by adding metadata. `create_threads` is also parent-context oriented and creates top-level threads, not subagents. Provider-native subagents are a separate class; they may have no child thread ID. The [MCP orchestration documentation](https://github.com/pingdotgg/t3code/blob/86dbf2abd18e631da1061f3a2489da603b2cc242/docs/orchestration-v2/orchestrator-mcp-server.md) specifies child-task modes, cancellation, questions, parent wakeups, and nested settlement. Render real lineage/IDs, status, source and pending work; label native or unknown relationships when not verifiable. Do not synthesize delegation or infer a task completed because its first provider turn ended.

Explicit launch `workspaceStrategy` binds a new `worktree`, an `existing_worktree`, or `root`; default is root. Local delegated `isolation: "worktree"` starts from the parent commit and does not copy uncommitted changes. A remote delegated target has different isolation limits. Resolve and display actual environment/project/checkout/branch from T3 before watching anything. Any Rust-scheduled parallel top-level runs must have explicit, independently chosen workspaces; shared checkout is a deliberate choice with race risk.

### Persistence and provenance

Upstream [`config.ts`](https://github.com/pingdotgg/t3code/blob/86dbf2abd18e631da1061f3a2489da603b2cc242/apps/server/src/config.ts) derives `<baseDir>/userdata/statev2.sqlite` for normal/explicit configuration, with a separate dev state path in the relevant dev case. [Architecture](https://github.com/pingdotgg/t3code/blob/86dbf2abd18e631da1061f3a2489da603b2cc242/docs/internals/overview.md) and [`EventStore.ts`](https://github.com/pingdotgg/t3code/blob/86dbf2abd18e631da1061f3a2489da603b2cc242/apps/server/src/orchestration-v2/EventStore.ts) describe committed events, projections, receipts and outbox effects in one transaction; provider effects run later, so command acceptance is not completion. The retained log is pruned (approximately a day, subject to maintenance and retained anchors): it is **not** a complete forever-replayable history. Projections survive pruning; raw provider diagnostics are bounded and are not canonical application state. Upstream DB schema/migrations are implementation details, and older T3 versions may not decode newer persisted events. Do not point a downgraded T3 at a newer database without a tested backup/restore plan.

The harness can store its own user-enabled data in a separate SQLite DB: environment ID, project/thread/run/item IDs, cursor and reducer snapshot, observed event envelope with source and receipt time, links, and bounded local artifact revisions. Unique keys should include environment identity plus the relevant upstream identity and sequence; keep per-thread checkpoints even though event sequence is environment-wide. Track whether a record is a live event, reconstructed snapshot, MCP page, or filesystem observation, and whether history is complete. A snapshot after a gap cannot reconstruct lost intermediate states. On disconnect or disk-full, expose an explicit gap and resynchronize; never silently assert an audit-complete history. Retention, content capture, deletion, and exports should be user-configurable; default to minimal metadata and avoid storing secrets or raw terminal content unnecessarily.

## Rust and visual integration plan

### Components and contracts

1. **Supervisor:** configure multiple environments, lifecycle ownership, connection states, backoff with jitter, bounded child processes, cancellation and health. Treat a connected socket as transport availability, not provider readiness. Track server version/capabilities and independently expose MCP-control and RPC-stream status.
2. **Control trait:** `list_projects`, `list_threads`, `read_thread_page`, `launch`, `send`, `wait`, `interrupt`, and request handling return typed results plus upstream IDs and explicit unsupported/denied/ambiguous errors. Implement MCP first; offer same-host CLI adapter for basic commands. Discovery and read-only access must not create provider sessions, install agents, or trigger login.
3. **Stream trait:** return a fallible stream of tagged `Snapshot`, `Event`, `Synchronized`, `CommandOutput`, `Gap`, and `ConnectionState`; preserve exact upstream JSON alongside a versioned normalized envelope only when retention is enabled. The TypeScript bridge uses the pinned client/schema and communicates through an explicit local IPC protocol: version handshake, request ID, environment/thread IDs, tagged response, error/cancel, bounded line size, and stdout reserved exclusively for machine frames. Stderr is bounded/redacted diagnostics. No assumed NDJSON framing on T3's own socket. Restrict inherited environment and authentication material, authenticate/protect any local IPC endpoint, and restart the bridge without restarting T3. Initial build must verify the TS package can actually be packaged independently; otherwise choose direct Rust RPC as a spike or use MCP polling.
4. **Reducer/read model:** stable keyed entities; serialized updates per environment/thread; snapshots replace the affected projection atomically; persist the cursor only with the corresponding committed state. Model pending approvals/questions, queued/running/completed/failed/interrupted runs, child tasks and completion settlement separately. Deduplicate control retries and stream replay. Expose unknown types without crashing; mark incomplete when an unknown could affect state.
5. **Fan-out:** bounded channels per browser; coalesce replaceable visual updates by item, never drop a terminal state or approval silently. On lag, send `reset`/gap and require a snapshot reload. Do not stall T3 ingestion on a slow browser. Expose snapshot + generation/cursor and SSE or WebSocket follow with a race-free handoff; browser reconnect uses its own harness cursor, not T3's cursor as if the two stores were identical. Test cancellation, idle heartbeat and replay-window exhaustion.
6. **Artifact adapter:** preserve existing [watcher](../src/watcher.rs), [events](../src/events.rs), [server](../src/server.rs), and [gallery assets](../assets/index.html). They currently watch indexed image/3D files and expose listing/live updates; they do not prove video/audio/code indexing, revision history, or agent provenance. Associate a file with a thread only by an authoritative checkout root plus environment and time, label it **observed in workspace**, and flag ambiguous shared workspaces. A time correlation is not causation. Canonicalize paths, enforce roots after symlink resolution and before serving/opening, and treat untrusted file contents as hostile. For remote files, use a separate explicit T3 asset/file capability with expiry and authorization; signed URLs are credentials and should not be persisted as durable paths.
7. **Visual read model:** connect thread/run timeline and tool cards to the live feed, preserving Inspector-observed patterns: folder/type filters, grid/list, current selection, activity strip, pause/catch-up, details, and optional history/compare. The [inventory](../inspector-feature-inventory/INSPECTOR-FEATURE-INVENTORY.md) distinguishes verified Inspector features from inferred behavior; do not reproduce its observed crashes or assume unverified parity. Existing gallery already has grid, watcher, filters and 3D previews. Media, code and history require explicit format, codec, size, security, and retention work beyond integration. Keep event ordering, source labels, and unavailable/gap states visible. Pause freezes the view or queues a bounded catch-up; it must not silently halt durable ingestion.

### Identity, commands, and failure states

Use `(environmentId, projectId, threadId, runId, itemId)` where available; preserve provider references as optional external IDs rather than primary keys. Distinguish command accepted, provider running, provider turn ended, run ended, pending request, background/delegated work, and final settlement. Expose pending authorization/question with original IDs and choices; never translate an approval click into a guessed provider payload. If request response is not supported by the chosen integration, deep-link to T3. A launch with lost response must enter `outcome_unknown` and offer reconciliation, not automatic retry. A send can retry with the same supported client request ID. A server restart, revoked credential, provider exit, tool error, version mismatch, queue overflow, dropped SSE consumer, and partial history each require a visible independent state.

## Delivery sequence and acceptance gates

1. **Contract spike:** record T3 version/commit and capabilities; run an isolated `t3 serve --base-dir <test-dir>` only with a controlled test project and an available mock/replay provider. Check CLI JSON and `--wait` exit paths; complete a normal outside MCP authorization; verify separately authorized RPC socket subscription. Capture sanitized fixtures including handshake, snapshot, live update, completion, interrupt, pending request and disconnect. Gate: demonstrate actual frames and auth before selecting the bridge or native Rust.
2. **Read-only vertical slice:** connect shell/thread snapshot + live updates to Rust with separate store and Axum SSE; gallery continues working. Measure update latency at bridge ingress, reducer commit and UI render, report distribution and missing/gap rate without promising a threshold before baseline. Gate: same visible state as T3 for one test run, including text replacement and unknown-event behavior; reconnect and server restart show correct resnapshot, not duplicate content.
3. **Control:** launch/send/wait/interrupt via discovered MCP tools and/or CLI with workspace binding, explicit modes and idempotency rules. Gate: test success, denied scope, provider unavailable, lost launch response, same send retry, pending user input and canceled waiter without unintended server cancellation.
4. **Workspace/lineage:** add family visualization and watch explicitly selected local checkouts, then a controlled test for app-owned child and provider-native subagent. Gate: distinguish root/fork/child/native/unrelated thread and correct shared-worktree ambiguity, including nested settlement and worktree cleanup ownership. Outside callers must not acquire parent-only delegation by inference.
5. **Inspector-style media/history:** design per-type ingestion and security/limits, bounded preview revision storage, and Compare. Gate: native rendered checks for supported image/3D/video/audio/code fixtures, failed/corrupt inputs, atomic writes, removals, burst load, pause/resume, timeline and selection. Evaluate media parity independently of T3 streaming.
6. **Release hardening:** test pinned minimum and current T3 builds, changed/missing schema fields, old-server feature flags, OAuth revocation, ticket renewal, DPoP if supported, process restart, offline duration past pruning, slow consumers, storage-full and privacy deletion. Add CI fixtures plus an optional real-provider smoke test; no production credentials or billing in default CI. Record supported T3 versions and refuse unsupported mutation while allowing safe fallback reads where proven.

## Alternatives and tradeoffs

| Option | Benefit | Cost / decision |
|---|---|---|
| CLI only | Lowest initial integration effort; no separate OAuth implementation on host | Final-result oriented and local; no proven live token/event stream, limited control surface. Good bootstrap/fallback. |
| Outside MCP only | Documented client interface, cross-machine control, least-privilege modes | Paging/polling is not a reliable live delta stream; no outside `delegate_task`, no direct `/ws` grant. Good control plane. |
| Pinned TS RPC bridge + Rust | Reuses actual Effect protocol, schemas and reconnection semantics while keeping product/backend in Rust | Requires shipping and versioning JS runtime/dependencies and separate environment auth; packaging and public compatibility unproven. Recommended streaming spike. |
| Native Rust Effect-RPC client | Single binary and direct ownership | Must reproduce framing, negotiation, schema evolution, ticket auth, stream lifecycle and compression accurately. Choose only after captured conformance tests justify maintenance. |
| Fork/extend T3 with stable sidecar API | Can add explicit versioned stream, cursor and grants | Ongoing fork/rebase, security and migration burden; propose upstream contract before committing to fork. |
| Direct provider CLIs/SDKs | Potentially provider-native detailed streaming | Reimplements provider adapters, permissions, project/worktree coordination, persistence and T3 lineage; separate product mode, not T3 integration. |
| Read T3 SQLite or tail internal logs | Convenient experiment | No supported API, racing WAL/schema migrations, pruned events and secret leakage; logs not authoritative. Reject for product integration. |

## Open questions to resolve before committing implementation

- What T3 release/build is installed on the target host, and which server feature flags and MCP tools does it expose? This plan pins source `main`, not the user's installed version.
- Can the official client runtime and its dependencies be packaged into a small independently runnable bridge at this commit, and what exact user-approved environment-session flow is viable for a headless local client? MCP OAuth alone cannot answer this.
- What exact Effect RPC frames, ping/ack and cancellation semantics occur across supported builds, and can upstream contract schemas be generated or tested against Rust without coupling to internal code? Measure on a controlled server.
- Which thread event types provide evolving text and tool detail for each selected provider and streaming setting? Are child projections and request responses available with the user's granted scopes? Test each provider; no cross-provider parity is assumed.
- What are acceptable stream latency, throughput, maximum workspaces, offline retention, memory/storage limits and artifact revision costs for this product? Set targets from measured baselines with the user.
- Is the intended product local-only or remote, and does the user want persistent captured content, multi-user access, or a filesystem-only mode? Each changes authorization, storage and privacy scope.
- Which supported upstream versions permit safe downgrade and retained-event decoding? Keep isolated state/backup and test migrations rather than relying on source compatibility alone.
